Théorie

Notes essentielles

Cette page regroupe les notions théoriques importantes rencontrées pendant le laboratoire. Elle ne reprend pas toutes les manipulations pas à pas, mais explique les concepts nécessaires pour comprendre le fonctionnement global du projet.

Les notions principales sont le DNS, les nameservers, les enregistrements CNAME, le reverse proxy, le HTTPS, le WAF, les cookies, les User-Agents et les redirections HTTP.

01 / Reverse Proxy

Un reverse proxy est un serveur intermédiaire placé devant le serveur réel. Dans ce labo, Cloudflare reçoit les requêtes des visiteurs avant de les transmettre à GitHub Pages.

Cela permet d’ajouter une couche de contrôle entre le client et l’hébergement : filtrage, HTTPS, cache, redirections et règles WAF.

02 / DNS & Nameservers

Le DNS permet de transformer un nom de domaine lisible en destination technique. Les nameservers indiquent quel service est responsable de la zone DNS du domaine.

En remplaçant les nameservers Namecheap par ceux de Cloudflare, Cloudflare devient responsable de la résolution DNS du domaine.

03 / CNAME

Un CNAME est un alias DNS. Il permet de faire pointer un nom de domaine ou un sous-domaine vers un autre nom de domaine.

Dans ce projet, les CNAME permettent de faire pointer le domaine personnalisé vers regalia00.github.io, qui correspond à GitHub Pages.

04 / Proxy Status

État Compréhension
Nuage orange Cloudflare agit comme reverse proxy et peut appliquer les règles WAF.
Nuage gris Cloudflare gère seulement le DNS, sans filtrer le trafic HTTP/HTTPS.

Le nuage orange est indispensable pour que le WAF puisse agir.

05 / HTTPS & SSL/TLS

HTTPS chiffre les échanges entre le navigateur et le site. Le protocole SSL/TLS garantit la confidentialité et l’intégrité des données échangées.

Cloudflare facilite cette partie en fournissant une couche HTTPS visible par le cadenas dans le navigateur.

06 / WAF Cloudflare

Un WAF, ou Web Application Firewall, analyse les requêtes HTTP avant qu’elles atteignent le serveur web. Il peut bloquer, défier ou laisser passer une requête selon des critères.

Champ Rôle Exemple d’utilisation
URI Path Filtrer une page précise Bloquer /page2.html
Country Filtrer selon le pays de l’adresse IP Bloquer les IP américaines
User-Agent Identifier navigateur, bot ou outil Détecter Chrome, curl ou sqlmap
Cookie Lire une valeur envoyée par le navigateur Autoriser superadmin=yes

07 / Ordre des règles

L’ordre des règles est très important. Cloudflare les évalue de haut en bas. Une règle trop générale placée trop haut peut bloquer une règle plus précise.

Par exemple, une règle qui bloque tous les navigateurs Chrome peut empêcher une autre règle d’autoriser les utilisateurs belges utilisant Chrome.

08 / Cookies

Un cookie est une donnée stockée côté navigateur et envoyée automatiquement dans les requêtes HTTP. Il peut contenir une valeur servant à identifier une session ou un rôle.

Dans le labo, le cookie superadmin=yes a été créé manuellement avec JavaScript via les Developer Tools.

Un cookie créé côté client peut être falsifié. Dans un vrai site, il doit être généré et signé par le serveur.

09 / Redirections HTTP

Une redirection HTTP indique au navigateur qu’il doit aller vers une autre URL. Cloudflare peut générer cette redirection avant que la requête n’atteigne GitHub Pages.

Dans le labo, les redirections permanentes utilisent le code HTTP 301 et le header Location.

10 / DNS ≠ Redirection

Le DNS sert à indiquer vers quel service envoyer une requête. Une redirection HTTP, elle, indique au navigateur de changer d’URL.

Élément Rôle
DNS Résout un nom de domaine vers une destination.
Redirection Renvoie le navigateur vers une autre URL.

Ce qu’il faut retenir

DNS

Le domaine doit savoir vers qui diriger le trafic.

Proxy

Cloudflare se place devant le site réel.

WAF

Les règles filtrent les requêtes avant l’hébergement.

Cookies

Ils peuvent être utilisés pour créer des règles d’accès.

Redirection

Cloudflare peut renvoyer une URL vers une autre destination.

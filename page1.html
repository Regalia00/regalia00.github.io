Labo Cloud Reverse Proxy

Reverse Proxy actif

Cette page présente le laboratoire Cloud Reverse Proxy réalisé avec GitHub Pages, Cloudflare et un nom de domaine personnalisé. Le but du laboratoire est de comprendre comment une requête web circule entre le navigateur d’un utilisateur, le DNS, Cloudflare et le serveur d’origine.

L’objectif n’était pas seulement d’obtenir un site fonctionnel, mais surtout de comprendre le rôle de chaque composant utilisé pendant la mise en place du projet.

01 / Objectif du laboratoire

Le laboratoire avait pour objectif de mettre en place un site web accessible via un nom de domaine personnalisé, tout en utilisant Cloudflare comme reverse proxy.

Cela permet d’observer concrètement comment Cloudflare peut protéger, filtrer et contrôler les requêtes avant qu’elles n’atteignent l’hébergement GitHub Pages.

02 / Achat du nom de domaine

Un nom de domaine a été acheté afin de disposer d’une adresse web personnalisée. Cette étape permet également de masquer l’adresse technique GitHub Pages.

  • Adresse publique plus professionnelle
  • Base nécessaire pour utiliser Cloudflare
  • Validation ICANN obligatoire après achat

03 / GitHub Pages

GitHub Pages sert d’hébergement pour le site statique HTML. Les fichiers du site sont stockés dans un repository GitHub puis publiés automatiquement.

Le site a été développé avec Notepad++ puis envoyé sur GitHub via upload manuel.

04 / Configuration DNS

Après l’ajout du domaine dans Cloudflare, les nameservers fournis par Cloudflare ont été configurés chez Namecheap.

  • Cloudflare devient gestionnaire DNS
  • Propagation DNS nécessaire
  • Création des enregistrements CNAME

05 / Reverse Proxy Cloudflare

Une fois le proxy Cloudflare activé, les visiteurs ne contactent plus directement GitHub Pages. Toutes les requêtes passent d’abord par Cloudflare.

Cela permet d’ajouter des protections WAF, du HTTPS et des règles de filtrage.

06 / Règles WAF

Plusieurs règles de sécurité ont été créées pendant le laboratoire afin de filtrer les accès à certaines pages du site.

  • Blocage selon le pays
  • Filtrage User-Agent Chrome
  • Challenge CAPTCHA
  • Contrôle via cookies

07 / Filtrage par cookie

Une règle Cloudflare a été créée afin de bloquer l’accès à une page si un cookie spécifique n’est pas présent dans la requête HTTP.

Le cookie a été ajouté manuellement via les Developer Tools du navigateur avec :

document.cookie="superadmin=yes"

08 / Redirections & sous-domaines

La dernière partie du laboratoire consistait à gérer les redirections et les sous-domaines avec les Redirect Rules Cloudflare.

Cette étape permet de rediriger automatiquement certaines URLs vers d’autres pages ou domaines.

Chemin simplifié d’une requête

01

L’utilisateur ouvre le site depuis son navigateur.

02

Le DNS Cloudflare reçoit la requête.

03

Cloudflare applique les règles WAF et le proxy.

04

GitHub Pages renvoie les fichiers HTML du site.

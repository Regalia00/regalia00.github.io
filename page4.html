Retour d’expérience

Cette page reprend les problèmes concrets rencontrés pendant le laboratoire. Elle ne présente pas seulement ce qui a fonctionné, mais aussi les erreurs, les hésitations et les imprévus qui ont permis de mieux comprendre le fonctionnement réel de Cloudflare, du DNS, de GitHub Pages et du WAF.

Elle sert aussi de rapport technique sous forme de site web. Les tableaux remplacent certaines captures d’écran en résumant clairement la configuration DNS, les règles WAF, les redirections et les tests réalisés.

Configuration DNS Cloudflare

Ces enregistrements permettent de relier le domaine personnalisé à GitHub Pages. Le mode Proxied signifie que le trafic passe par Cloudflare avant d’arriver sur l’hébergement réel.

Type Nom Cible Proxy Rôle
CNAME www regalia00.github.io Proxied Adresse principale du site
CNAME @ regalia00.github.io Proxied Domaine racine
CNAME xena regalia00.github.io Proxied Sous-domaine utilisé pour la redirection
CNAME xyz regalia00.github.io Proxied Sous-domaine utilisé pour la redirection

Règles WAF / sécurité

Les règles WAF permettent à Cloudflare d’analyser les requêtes HTTP avant GitHub Pages. Elles servent à bloquer, filtrer ou demander une vérification selon des conditions précises.

Objectif Condition Action Résultat attendu
Bloquer page2.html URI Path equals /page2.html Block La page est inaccessible sans exception.
Géoblocage Country equals United States AND URI Path equals /page1.html Block Les IP américaines ne peuvent pas accéder à page1.html.
Filtrage Chrome User-Agent contains Chrome Block Les navigateurs basés sur Chrome sont bloqués.
Challenge Belgique + Chrome Country equals Belgium AND User-Agent contains Chrome AND URI Path equals /page2.html Managed Challenge L’utilisateur doit résoudre un challenge avant l’accès.
Filtrage par cookie URI Path equals /page2.html AND NOT Cookie contains superadmin=yes Block Sans le cookie attendu, l’accès est refusé.

Règles de redirection

Les redirections sont configurées dans Cloudflare afin de renvoyer automatiquement certaines URLs vers une autre destination. Elles utilisent des codes HTTP, notamment le code 301 pour une redirection permanente.

Source Destination Type Détail important
www.thibault-esr-itscm.xyz/recherche.html https://google.be 301 La page n’existe pas réellement sur GitHub Pages.
xena.thibault-esr-itscm.xyz/* www.thibault-esr-itscm.xyz/* 301 L’URI est conservée pendant la redirection.
xyz.thibault-esr-itscm.xyz/* www.thibault-esr-itscm.xyz/* 301 Une seule règle gère les deux sous-domaines.

01 / Service de nom de domaine indisponible

Ce qui s’est passé :

Le labo proposait un service d’hébergement de nom de domaine, mais celui-ci était hors service ou inutilisable au moment de la réalisation. Cette étape a donc bloqué le déroulement normal du labo dès le départ.

Ce que j’ai fait :

Il a fallu improviser et choisir rapidement une alternative fiable, compatible avec Cloudflare et pas trop chère. J’ai donc utilisé Namecheap pour acheter le domaine thibault-esr-itscm.xyz. Même si ce n’était pas exactement le service prévu dans le document, cela permettait d’atteindre le même objectif : disposer d’un vrai domaine public à relier à Cloudflare.

02 / Propagation DNS pas immédiate

Ce qui s’est passé :

Après avoir remplacé les nameservers Namecheap par ceux de Cloudflare, je m’attendais à voir le changement directement. Pourtant, avec nslookup, les anciens DNS apparaissaient encore.

Ce que j’ai compris :

Au début, j’ai cru que j’avais fait une erreur dans la configuration ou que les nameservers avaient été mal copiés. En réalité, la configuration était correcte, mais la propagation DNS n’était pas encore terminée.

Les informations DNS peuvent rester en cache chez différents résolveurs pendant un certain temps. Cela signifie qu’un changement effectué chez Namecheap ou Cloudflare n’est pas forcément visible immédiatement depuis un terminal. Il faut attendre que les caches se mettent à jour avant que les nouveaux nameservers Cloudflare apparaissent partout.

03 / GitHub Pages affichait une erreur 404

Ce qui s’est passé :

Au début, le site GitHub Pages ne s’affichait pas et renvoyait une erreur 404. Ce n’était pas très parlant, car le fichier HTML existait bien.

Ce que j’ai corrigé :

Le problème venait de la configuration GitHub Pages et du nom du repository. Pour un site utilisateur GitHub Pages, le repository devait correspondre au format attendu : regalia00.github.io. Une fois le bon repository utilisé et GitHub Pages activé, le site a commencé à fonctionner.

04 / Notepad++ et GitHub Web

Différence avec le labo :

Le labo demandait de créer les pages HTML avec Notepad++. Au départ, certaines modifications ont été faites directement depuis l’interface web de GitHub, ce qui fonctionnait, mais ne suivait pas exactement la méthode demandée.

Ce que j’ai retenu :

Techniquement, les deux méthodes fonctionnent, mais l’objectif du labo était aussi de comprendre la création locale des fichiers HTML. J’ai donc repris la logique avec Notepad++ puis l’envoi des fichiers vers GitHub.

05 / Proxy Cloudflare activé trop tôt ou trop tard

Point délicat :

Pour que GitHub valide correctement le domaine personnalisé, le proxy Cloudflare devait d’abord rester désactivé, c’est-à-dire en mode DNS only avec le nuage gris.

Ce que j’ai compris :

La bonne logique est : créer le CNAME, laisser le proxy désactivé, configurer le custom domain dans GitHub Pages, attendre la validation, puis revenir dans Cloudflare pour activer le proxy orange. À partir de ce moment, Cloudflare devient vraiment le reverse proxy.

06 / Mauvaise configuration DNS

Ce qui s’est passé :

À un moment, une erreur dans les enregistrements DNS a rendu le site inaccessible. Cela montre qu’une petite erreur dans un CNAME ou dans le proxy status peut casser tout l’accès au site.

Ce que j’ai corrigé :

Les enregistrements ont été vérifiés et corrigés pour faire pointer www.thibault-esr-itscm.xyz et le domaine racine vers regalia00.github.io. Une fois les records DNS cohérents, le site a de nouveau répondu correctement.

07 / Règles WAF plus compliquées que prévu

Ce qui a été difficile :

Créer les règles Cloudflare n’était pas aussi simple que prévu. Il fallait choisir le bon champ, le bon opérateur, la bonne action et surtout comprendre dans quel ordre les règles étaient lues.

Ce que j’ai compris :

Une règle WAF fonctionne comme une condition : si la requête correspond, Cloudflare applique l’action. Par exemple, URI Path equals /page2.html permet de cibler précisément une page. Il faut donc bien réfléchir à la logique avant de créer la règle.

08 / Conflit entre règles Cloudflare

Erreur rencontrée :

Une règle bloquait tous les navigateurs Chrome, alors qu’une autre règle devait justement autoriser certains utilisateurs Chrome belges avec un challenge. Les deux règles se contredisaient.

Ce que j’ai appris :

L’ordre et la logique des règles sont essentiels. Une règle trop générale peut empêcher une règle plus précise de fonctionner. Il faut donc placer les exceptions avant les blocages généraux ou désactiver les règles qui entrent en conflit.

09 / Filtrage par cookie

Ce qui posait question :

Le labo demandait de filtrer sur base d’un cookie superadmin=yes, mais le site étant statique, il n’y avait aucun serveur capable de créer automatiquement ce cookie.

Ce que j’ai fait :

Le cookie a été créé manuellement depuis les Developer Tools du navigateur avec la commande : 

document.cookie="superadmin=yes"

Ensuite, une règle Cloudflare a été créée pour bloquer l’accès à une page si ce cookie n’était pas présent. Cela montre bien que Cloudflare peut lire les cookies envoyés dans les requêtes HTTP.

10 / Sécurité réelle des cookies

Limite importante :

En créant le cookie manuellement, on voit directement qu’un cookie côté client peut être modifié par l’utilisateur. Ce n’est donc pas une vraie authentification sécurisée.

Ce que j’ai retenu :

Dans ce labo, le cookie sert surtout à comprendre le principe. Dans un vrai site, un cookie d’authentification devrait être généré par le serveur, signé, protégé et lié à une vraie session.

11 / Redirection des sous-domaines

Ce qui était piégeux :

La consigne demandait de rediriger les sous-domaines xena et xyz vers www, tout en conservant l’URI. Il ne fallait donc pas simplement rediriger vers la page d’accueil.

Solution appliquée :

Une règle de redirection dynamique a été utilisée dans Cloudflare : 

concat("https://www.thibault-esr-itscm.xyz", http.request.uri.path)

Grâce à cela, une URL comme xena.thibault-esr-itscm.xyz/page1.html redirige bien vers www.thibault-esr-itscm.xyz/page1.html.

12 / Ancienne syntaxe de redirection non valide

Ce qui s’est passé :

La syntaxe simple avec une variable comme ${uri} ne fonctionnait pas dans l’interface moderne de Cloudflare.

Ce que j’ai compris :

Cloudflare utilise maintenant son propre langage d’expression pour certaines règles. Il faut donc utiliser des variables comme http.request.uri.path et une fonction comme concat() pour reconstruire dynamiquement l’URL finale.
